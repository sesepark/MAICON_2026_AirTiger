# perception

## 미션별 perception이 담당해야 하는 부분

아래는 박세환이 생각했을 때, 현재 5개 노드 구조에서 이 노드가 반드시 맡아야 하는 기능이다. 다른 노드와 담당이 겹치거나 판단이 필요한 부분은 여기에 적지 않았다. 그런 부분은 대회 중 회의·토론을 통해 정한다.

### 미션 2 — 지정표적 타격

- 영상에서 지정표적을 탐지·식별하고 지시받은 대상을 추적한다.
- `/mil/gimbal`로 짐벌을 제어하고 조준 상태를 전달한다.

### 미션 3 — 전장객체 인식

- 영상에서 대회 지정 객체를 탐지하고 종류를 분류한다.
- 인식 결과를 관측 정보로 전달한다.

### 미션 4 — 상대 UGV 타격

- 영상에서 UGV를 탐지하고 피아·개체 식별 결과를 전달한다.
- 지시받은 대상을 추적하고 짐벌을 제어해 조준 상태를 전달한다.

### 미션 6 — 전장 위험도 분석

- 영상에서 확인할 수 있는 상대 UGV와 활동·표시 상태 등의 관측 정보를 산출한다.
- 관측 출처·시각을 보존하고, 식별할 수 없는 상태는 미확인으로 전달한다.

## 역할 및 구현 상태

객체 인식·관측 정보 정리·지정 대상 추적·짐벌 제어를 담당한다.

초기 생성 시점(2026-11-15)에는 패키지 껍데기만 작성했다. 최신 구현 상태는 YAML의 해당 노드 항목과 실제 코드로 확인한다.

### 사진 판독 서비스 (2026-11-18, 구현 중)

supervisor가 사진 한 장을 보내면 그 안의 그림(상자 옆면)들을 왼쪽부터 답한다. 규격은 [요청사항 2절](../supervisor/docs/요청사항.md)과 `ClassifyImage.srv` · `Picture.msg`.

켜는 명령:

```bash
ros2 run perception perception_node --ros-args -p model_path:=/home/ws/team/models/pictures.engine
```

| 파일 | 내용 |
|---|---|
| `perception/node.py` | 노드. `/team/perception/classify_image` 제공, `/team/node_status` 발행 |
| `perception/pictures.py` | 탐지 결과 → 그림 목록 계산 (왼쪽부터 · unknown · cut_off). ROS 없이 시험 가능 |
| `perception/detector.py` | 모델 감싸개 (ultralytics `.engine` / `.pt`) |
| `perception/zoom.py` | 작은(먼) 그림을 잘라 키워 다시 판독. ROS · 모델 없이 시험 가능 (`test/test_zoom.py`) |
| `tools/eval_by_size.py` | 그림 크기별 · 거리 모사 평가 도구 |
| `test/test_pictures.py` | `python3 -m unittest discover -s test` |

| 매개변수 | 기본값 | 뜻 |
|---|---|---|
| `model_path` | `/home/ws/team/models/pictures.engine` | 가중치. 없으면 같은 이름의 `.pt` |
| `min_confidence` | 0.5 | 이보다 낮은 탐지는 빼지 않고 `unknown` 으로 답한다 |
| `detect_conf` | 0.15 | 모델 탐지 임계값. 그림을 놓치지 않게 낮게 둔다 |
| `imgsz` | 640 | 추론 해상도 |
| `zoom_max_height` | 96 | 박스 높이가 이 픽셀 이하인 그림은 둘레를 잘라 키워 한 번 더 판독한다 (아래 「먼 그림 확대 재판독」). 0 이면 끔 |
| `zoom_fill` | 0.25 | 잘라 낸 창에서 그림의 긴 변이 차지할 비율 |
| `zoom_limit` | 4 | 사진 한 장에서 다시 보는 그림 수의 상한 (작은 것부터) |

- 모델은 **그림 한 장 전체**를 한 박스로 잡는 10종 탐지 모델이다: 객체 6 · 지정표적 3 · `non_object`. `unknown` 은 모델 클래스가 아니라 점수가 낮을 때 노드가 붙인다. 학습은 별도 저장소(모델 레포)에서 한다.
- 준비되면 `/team/node_status` 가 `READY`. 모델 파일이 없거나 `torch` · `ultralytics` 가 없으면 `ERROR`, 10종 중 못 내는 종류가 있으면 `DEGRADED`.
- 로봇에서 확인 (2026-11-19 12:20, Jetson, TensorRT 엔진): 빌드 5초, 상태 `READY`, 저장한 사진 18장으로 `classify_image` 를 불러 호출당 평균 55 ms (첫 호출 117 ms). 점검 도구는 `임시_테스트_파일/perception_service_check.py`. 카메라 실시간 영상 · supervisor 와 이어서는 아직 안 해 봤다.
- 미구현: `field_map`, `observations` 발행, `TrackTarget`, 짐벌 제어.

#### 먼 그림 확대 재판독 (2026-11-19)

가까운 그림은 거의 다 맞히는데 먼 그림은 종류를 틀리거나 `unknown` 으로 나간다. 카메라가 640x480 이고 모델도 640 으로 보므로
줄여서 잃는 것은 없다 — 먼 그림은 원래 작게 찍히고, 모델은 대부분 크게 찍힌 그림으로 배웠다 (크기 분포가 다르다).
그래서 작은 그림은 둘레를 잘라 모델 입력 크기로 키워 한 번 더 본다 (`perception/zoom.py`).

- 박스 자리 · 개수 · 순서는 처음 탐지 그대로이고 **종류 · 점수만** 바뀐다. 다시 본 답의 점수가 처음보다 높을 때만 바꾼다
  (같은 자리에 그림이 없거나 점수가 낮으면 처음 답 그대로 — 가까이서 이미 맞힌 답이 덮이지 않는다).
- `classify_image` 의 그림 목록에만 쓴다. detail 끝의 수광부(`sensors=[...]`) · `read_ugvs` · `locate_sensors` 는 처음 탐지 그대로다.
- 시간: 다시 보는 그림 하나에 추론 한 번 (로봇 TensorRT 약 35 ms) → 사진 한 장에 최대 `zoom_limit`(4)번, 약 +140 ms. supervisor 마감 5초.
- 같은 모델 · 같은 입력 크기(640)라 엔진을 다시 만들 필요가 없다.

재는 도구 `tools/eval_by_size.py` — 노드와 같은 길(`detect` → `zoom.refine` → `build_pictures`)로 그림 크기별 맞음 · unknown · 다른 종류 · 놓침을 센다.

```
python tools/eval_by_size.py --weights pictures.pt --data <YOLO 데이터셋 폴더들> --shrink 1,0.5,0.33,0.25 --zoom-max-height 96 --compare
```

- `--shrink`(거리 모사): 라벨이 붙은 그림은 대부분 가깝다. 사진을 s 배로 줄여 같은 크기 회색 화면 가운데에 놓아 약 1/s 배 멀리 찍힌 것처럼 만든다.
  원근 · 초점 · 조명은 모사하지 못하므로 실제 먼 그림 사진으로 다시 재야 한다.
- 결과 (2026-11-19, 로봇 사진 123장 · 라벨 그림 130개, 모델 레포 `data/ugv_dataset_*`, 종류까지 맞은 비율, conf ≥ 0.5):

| 모델 | 확대 | 원본 | 2배 멀리 | 3배 멀리 | 4배 멀리 |
|---|---|---|---|---|---|
| `pictures_v2_synth_only` (이 사진을 본 적 없음) | 끔 | 98.5 % | 92.3 % | 73.1 % | 53.8 % |
| | 켬 | 99.2 % | 98.5 % | 96.2 % | 90.0 % |
| `pictures_v2` (운용 모델. 123장 중 98장을 학습에 씀 — 점수가 부풀려짐) | 끔 | 97.7 % | 96.2 % | 92.3 % | 74.6 % |
| | 켬 | 99.2 % | 98.5 % | 97.7 % | 94.6 % |

  - `fill` 을 바꿔 본 것 (synth_only, 4배 멀리): 0.5 → 80.8 % · 0.4 → 82.3 % · 0.3 → 89.2 % · 0.25 → 90.0 % · 0.2 → 91.5 %. 0.2 ~ 0.3 의 차이는 그림 2 ~ 3개라 가운데 값을 골랐다.
  - 처음엔 다시 본 답을 늘 썼는데 원본에서 98.5 → 96.2 % 로 떨어졌다 (맞힌 답이 낮은 점수의 답으로 덮임) → 점수가 높을 때만 바꾸게 했다.
  - 이 사진들의 라벨은 그림 일부에만 붙어 있다 (UGV 부품만 친 사진도 있음, 그림 속 물체만 감싼 예전 방식). 그래서 오탐 수 · 프레임 완전일치는 이 데이터로는 뜻이 없다.
    확대 재판독은 박스를 더하거나 빼지 않으므로 오탐 수는 그대로다.
  - 남은 실패: 4배 멀리(정답 상자 24 px 미만)에서 놓침 3 % · 다른 종류 3 %. 더 줄이려면 모델 쪽(작은 그림 · 화질 저하 증강, 먼 거리 실제 사진)이다.
- 미검증: 로봇(TensorRT 엔진)에서의 시간 · 실제 먼 그림 사진. 전체 그림으로 다시 라벨링한 벤치마크(모델 레포 `bench/`, GPU 서버의 `real_v4`)로도 재야 한다.

### UGV 상태 판독 서비스 (2026-11-19, 구현 중 — 색 판독)

supervisor가 사진 한 장을 보내면 찍힌 UGV들을 답한다(`/team/perception/read_ugvs`, [요청사항 2절 8번](../supervisor/docs/요청사항.md), `ReadUgvs.srv` · `UgvState.msg`).

| 파일 | 내용 |
|---|---|
| `perception/ugvs.py` | 탐지 결과 → UGV 목록 계산. 안테나 색 · 검은 띠 수 · LED 색 판독, 모델이 놓친 색 덮개 찾기 |
| `test/test_ugvs.py` | 단위 시험 (합성 영상) |

| 값 | 읽는 방법 | 못 읽는 경우 |
|---|---|---|
| 위치 · 크기 | 모델의 `ugv` 박스 | — |
| `camp` | 안테나에 끼운 색 덮개: 빨강 = `RED`, 파랑 = `BLUE`. 모델이 안테나를 못 찾으면 UGV 박스 둘레에서 덮개 모양(진한 빨강 · 파랑의 길고 가는 세로 토막)을 직접 찾는다 | 덮개가 안 보임 · 색이 약함 · 안테나끼리 색이 다름 → `""` |
| `callsign` | 색 덮개의 검은 띠 수 → `R-2` 처럼. 덮개를 따라 내려가며 색이 약해지는 골을 센다 | 덮개가 사진에서 40 픽셀보다 짧음(UGV 박스 높이 대략 200 픽셀 미만) · 안테나끼리 띠 수가 다름 → `""` |
| `lives` | 뒷면 LED 막대의 색: 파랑 4 · 초록 3 · 노랑 2 · 주황 1 · 빨강 0 (공식 자료 prestudy1: 파(정상) · 초(1) · 노(2) · 주(3) · 빨(4) = 유효피격 수). 모델이 막대를 못 찾으면 차체 아래쪽에서 하얗게 번진 가로 막대 + 둘레의 색 번짐을 직접 찾는다 | 뒷면이 안 보임 · 색 번짐이 안 남음 → `-1` |
| `ammo` | 읽지 않는다 | 항상 `-1` (LED 가 번져 켜진 개수를 셀 수 없다) |

- **모델이 둘이다.** 그림 판독은 `model_path`, UGV 판독은 `ugv_model_path`(기본 `/home/ws/team/models/ugv_parts.engine`, 없으면 같은 이름의 `.pt`)를 쓴다. UGV 판독용 모델은 `ugv` 외에 `antenna` · `led_bar` · `ugv_sensor` 를 함께 찾는다.
  부품 클래스를 그림 모델에 합쳐 학습하면 그림 인식이 나빠져서 따로 두었다 (2026-11-19 팀 평가 도구 기준: 프레임 전체 정답 0.908 → 0.745).
- `ugv_model_path` 파일이 없으면 그림 모델로 UGV 위치만 답한다 (그림 모델에는 안테나 · LED 클래스가 없어 네 값은 모두 못 읽음).
- 쓰는 모델에 `ugv` 클래스가 없으면 `ok = false`, `detail = "model has no ugv class"`. 빈 목록에 `ok = true`는 "UGV가 없다"는 뜻이라 쓰지 않는다.
- 매개변수 `min_ugv_confidence`(기본 0.35): 이보다 낮은 탐지는 UGV로 치지 않는다.
- `classify_image`는 `ugv` · `target_sensor` · `antenna` · `led_bar` · `ugv_sensor` 처럼 그림이 아닌 클래스를 그림 목록에서 뺀다.
- 그중 수광부(`target_sensor`) 탐지는 답의 `detail` 끝에 싣는다 (2026-11-19): `2 pictures in 56 ms | sensors=[[x_center, y_center, width, height, confidence], ...]` — 사진 크기에 대한 비율, 왼쪽부터, 없으면 `sensors=[]`. supervisor 가 지정표적에 레이저를 겨눌 때 쓴다 (`pictures.build_sensors` · `sensors_text`, 매개변수 `min_sensor_confidence` 기본 0.15). 메시지 정의는 바꾸지 않았다.

**확인한 것 (2026-11-19)**: 실제 로봇 프레임 14장(그중 2장은 학습에 안 쓴 것)에서 UGV · 안테나 · LED 막대를 모두 찾았고, 빨강 진영 로봇을 9장에서 `RED`로 읽고 틀린 진영으로 읽은 것은 없었다. `lives`는 5장에서 값이 나왔다. 같은 14장을 로봇에서 `read_ugvs` 서비스로 불러도 결과가 같았고(`RED` 9장, 틀린 진영 없음) 호출당 평균 54 ms 였다.

**진영 · 호출부호를 실제 경기 사진으로 다시 맞춤 (2026-11-20)**: 상대 안테나에 피아식별띠가 있던 7판(본선 경기장 11-19 16:55 ~ 18:06 의 6판 + 연습 경기장 2 의 11-20 00:31 판)의 supervisor 사진 1,526장에 부품 모델(pictures_m6_v1, 그대로)과 판독 코드를 돌렸다.

| UGV 박스 높이 | UGV 수 | `camp` 읽음 (전 → 후) | `callsign` 읽음 (전 → 후) |
|---|---|---|---|
| 200 픽셀 이상 | 387 | 75 % → 95 % | 39 % → 91 % |
| 120 ~ 200 | 76 | 71 % → 82 % | 12 % → 26 % |
| 60 ~ 120 | 186 | 31 % → 71 % | 4 % → 2 % |
| 60 미만 | 50 | 4 % → 18 % | 0 % |

전의 `callsign` 은 읽힌 것도 자주 틀렸다 — 17:38 판에서 전에는 `B-1` 19 · `B-2` 15 · `B-3` 12 로 갈렸는데 지금은 `B-3` 90 · `B-2` 2 · `B-1` 1 이다 (그 판의 파랑 상대는 눈으로 봐도 띠 3개).
같은 코드를 로봇에서 엔진(`ugv_parts.engine`)으로 두 판(334장)에 돌려도 거의 같은 답이 나왔고(17:38 판 `B-3` 89 · `R-2` 38), 걸린 시간은 모델 39 ms + 판독 평균 9 ms(최대 37 ms)였다. ROS 서비스로 부른 것은 아니다.

- 바꾼 것 둘: ① 띠 세기 — 전에는 "어두운 줄이 2줄 이상"을 셌는데 실제 띠는 번져서 덜 어둡고 가늘어 적게 셌다. 지금은 덮개의 가운데 선을 따라 색 세기를 재고 둘레보다 45 % 넘게 약해진 골을 센다 (덮개 위쪽 10 ~ 68 % 구간, 서로 붙은 골들만). ② 모델이 안테나를 놓치면 색으로 덮개를 직접 찾는다 (`ugvs.find_sleeves`) — 부품 모델은 빨강 로봇 14장으로만 배워 본선 사진에서 가까운 UGV 의 안테나를 자주 놓쳤다 (특히 파랑).
- 맞는지 본 방법: 정답표는 없다. ① 한 UGV 의 두 안테나가 같은 수를 낸 비율 30 / 47 → 110 / 118. ② 무작위로 뽑은 안테나 40개를 확대해 눈으로 셈 — 띠가 뚜렷한 33개는 모두 맞았고, 5개는 흔들린 사진이라 눈으로도 셀 수 없었고, 2개는 판독이 "못 읽음"으로 답했다(하나는 덮개가 아닌 탐지).
- 틀리는 경우: 달리며 찍혀 흔들린 사진, 덮개 앞을 전선 · 다른 물체가 가로지를 때. 한 장의 답을 그대로 믿지 말고 여러 장에서 많이 나온 값을 쓰는 편이 안전하다.
- 그 7판의 사진과 평가 스크립트는 저장소에 넣지 않았다 (대회 자료). 평가는 GPU 데스크톱에서 했다.

### 수광센서 자리 서비스 (2026-11-19, 구현 중)

사진 속 수광센서의 자리와 그것이 어디에 붙은 것인지(지정표적 · UGV)를 알려 준다. supervisor 가 상대 UGV 를 따라가며 쏠 때 쓴다 (선택 사항, 기본 끔). 지정표적(M2) 조준은 이 서비스가 아니라 `classify_image` 답의 `detail` 에 실린 수광부 목록을 쓴다 — 그 목록에서는 UGV 상자(점수 0.5 이상) 안의 수광부를 뺀다.

| 항목 | 내용 |
|---|---|
| 서비스 | `/team/perception/locate_sensors` (`team_interfaces/srv/LocateSensors`, 센서 하나 = `SensorSpot.msg`) |
| 계산 | `perception/sensors.py` (ROS · 모델 없이 시험 가능), 노드 연결은 `node.py` 의 `_locate_sensors` |
| 답 | 센서마다 자리 · 크기 · 점수와 `owner`(`target` / `ugv` / `unknown`), 붙어 있는 것(`host_kind` = 그림 종류 또는 `ugv`, UGV 면 `camp` · `callsign`) |
| 모델 | 그림 모델(`target_sensor` · `ugv` · 그림)을 돌리고, UGV 부품 모델(`ugv_model_path`)이 따로 있으면 그것도 돌린다(`ugv_sensor` · 안테나 색) |

- `owner` 는 모델의 클래스 이름이 아니라 **자리**로 정한다. 지정표적의 센서와 UGV 의 센서는 생김새가 같아 모델이 섞기 때문이다: 센서 가운데가 UGV 박스 안이면 `ugv`, 그림 박스(35% 넓힌 것) 안이면 `target`, 어디에도 안 붙어 있으면 모델이 `target_sensor` 라 했을 때만 `target`.
- 두 모델이 같은 센서를 찾으면 점수 높은 하나만 남긴다. 점수 0.25 미만은 뺀다.
- 시험: `test/test_sensors.py` 7개 (합성 탐지). **실제 사진 · 로봇에서는 확인하지 못했다** — 표적 수광센서가 그림 박스에서 얼마나 떨어져 붙어 있는지(35% 여유가 맞는지)는 실제 프레임으로 봐야 한다.

### 드론 화면 → 경기장 경계 (구현 중 — 노드 연결은 아래 「드론 사진 → 지도 발행」)

`perception/drone_boundary.py` — 드론 화면 한 장에서 경기장 경계(화면 픽셀 ↔ 경기장 좌표 m)를 자동으로 정한다. ROS 노드 · 토픽은 아직 없다 (함수만).

- 바닥 흰 선(세로 구역선 5 · 가로 줄 경계 2 · 중앙 원)의 **모양**으로 찾는다. 화면 픽셀 위치를 외우지 않는다 → 경기 전에 볼 수 없는 main 카메라용.
- 카메라 모델: 렌즈 왜곡(k1 · k2 · 픽셀 가로세로 비 · 중심) + 바닥 사영 변환. 확장 렌즈 모델이 이상하면 단순 모델(k1)로 물러난다.
- 좌표계는 sim-strategy `team/navigation/fieldmap.py` 와 같다. 경기장 6.12 × 5.00 m (공식 자료 「약」 값).
- 검증 (2026-11-18 연습 경기장): 경기장 곳곳 A4 용지 12장으로 축척 σ 3~4 % (단순 모델은 10 %). 시험 그림 4장 `test/test_drone_boundary.py`.
  수집 화면 일괄 시험은 단순 모델 때 한 것(test2 245/245, test1 177/178 중 오답 3)이고, 확장 모델로는 아직 다시 하지 않았다.
- 알려진 한계: 확장 렌즈값(k2 · 픽셀 비)이 화면에 따라 흔들린다 (test1 픽셀 비 0.58~0.87, 모서리 ±12 px) · 사람이 선을 가린 화면에서 오답 ·
  박스 · UGV 처럼 높이 있는 물체는 이 대응(바닥 높이 0)으로 바로 옮기면 안 된다.

```
python tools/detect_boundary.py 화면.jpg            # 경계 JSON + 전후 그림 (boundary_out/)
python tools/detect_boundary.py --fetch test1        # 연습 서버에서 한 장 (MAICON_MISSION_CODE 필요)
python tools/collect_drone_frames.py --interval 10   # 연습 화면 수집
python3 -m unittest discover -s test -p "test_drone_boundary.py"   # 시험 (ROS 불필요, 약 30초)
```

### 드론 화면 수집 · 박스 라벨링 웹 화면 (2026-11-19, 학습 데이터용 — 경기 중 코드 아님)

`tools/label_drone_frames.py` — 웹 화면에서 「시작 · 정지」 로 드론 화면을 7초마다 한 장씩 모으고(그사이 박스 배치를 바꾼다), 받는 대로
**지도와 같은 좌표의 그림(`undist_map`)** 으로 바꿔서, 거기에 박스 윗면을 라벨링해 YOLO OBB 데이터셋으로 내보낸다. 라벨만 달면 그대로 지도의 상자 자리가 된다. 수집은 `tools/collect_drone_frames.py` 를 띄워서 하고(임무코드는 환경변수로 넘김),
왜곡 펴기는 `drone_boundary` 계수를 그대로 쓴다 (`tools/undistort_drone_frames.py --watch` 가 수집을 따라간다).

python3 -m unittest discover -s test -p "test_label_drone_frames.py"   # 시험 (가짜 드론 서버, 약 5초)

- 저장: `data/drone_sessions/<시각>_<이름>/` (수집기 출력 그대로) · 전처리 `<세션>/undist_<mode>/` · 라벨 `<세션>/labels/<그림 종류>/<camera>/<이름>.json` ·
  내보내기 `data/drone_datasets/`. 모두 `data/` 밑이라 git 에 안 올라간다. 기존 `data/drone_frames` 도 세션 목록에 같이 나온다.
- 서버 · 임무코드: 기본 서버는 연습 서버 `http://<서버IP>:8100` (test1 · test2. `main` 은 이 포트에서 422 이고, 포트 8000 에서 우리 경기 중에만 나온다 —
  2026-11-19 확인). 임무코드는 저장소에 올리지 않는다 — `data/label_drone_frames.json` `{"mission_code": "...", "server": "...", "interval_s": 7}` (git 에 안 올라감)
  이나 환경변수 `MAICON_MISSION_CODE` 에 두면 화면에서 넣지 않아도 된다.
- 수집: 카메라마다 마지막 장 · 저장 수 · 실패 이유(409 = 테스트 모드 꺼짐이나 포트, 401 = 임무코드)가 보인다. 디스크 여유가 2 GB 아래면 멈춘다.
  간격(기본 7초)은 화면에서 바꾼다.
  **박스 배치가 바뀌어야 데이터가 는다** — 배치를 바꿀 때마다 세션 이름을 바꿔 새로 시작하면 내보내기의 검증 나누기가 배치(세션) 단위가 된다.
- 전처리 `map` (라벨용, 기본): 렌즈 왜곡을 펴고 **경기장 테두리(x 0 ~ 6.12 · y 0 ~ 5.00 m, 경계가 잰 값)로 잘라** 1 cm/px (612 × 500) 로 편다.
  그림의 평면은 **상자 윗면 높이 0.40 m** 다 — 카메라(정중앙 위, 높이 Hc)에서 높이 있는 점이 바깥으로 밀려 찍히는 만큼(`drone_boxes` 와 같은 s = Hc/(Hc−0.4))
  되돌려 그리므로, 상자 윗면이 자기 바닥 자리 바로 위에 40 × 40 px 로 찍힌다. 픽셀 (u, v) → 지도 (u/100, 5.00 − v/100) m, 윗면 네 꼭짓점 가운데 = 지도
  (`FieldMap.boxes`, frame `arena`)의 상자 가운데. 바닥 그림(선 · 원)은 높이가 달라 가운데 쪽으로 줄어 보인다.
  카메라 높이는 고정 카메라라 카메라마다 한 번 잰다: 여러 장(기본 12)에서 `drone_boxes` 가 옆면 폭으로 잰 값의 중앙값 → `data/drone_camera_heights.json`
  (한 장은 ±15 % 흔들린다. 2026-11-19 test1 2.95 m · test2 2.54 m). `--camera-height test1=2.95` 로 정할 수도 있다.
  확인 (2026-11-19 실제 test1 · test2 화면): 같은 높이로 `drone_boxes` 가 찾은 상자 자리(40 cm 정사각형)를 map 그림에 그리면 윗면과 겹친다.
  다른 모드: `top` = 바닥 평면 위에서 본 그림 (윗면이 약 19 % 크고 바깥으로 밀림) · `lens` = 렌즈 왜곡만.
  계수는 카메라마다 바닥 흰 선으로 한 번 맞추고 300 장마다 다시 맞춰 본다. `calib.json` 의 `out_to_field` = 출력 픽셀 → 경기장 (m), `plane_h` = 그 평면 높이.

### 드론 화면 → 상자 위치 (구현 중 — 노드 연결은 아래 「드론 사진 → 지도 발행」)

`perception/drone_boxes.py` — 드론 화면 한 장과 위의 경계 결과로 상자(40 cm 정육면체)의 가운데 좌표(경기장 m)를 낸다.
`perception/drone_field_map.py` — 그 결과를 **`team_interfaces/FieldMap` 형식**으로 바꾼다 (`/team/perception/field_map` 으로 내보낼 내용).
노드에 붙여 토픽으로 내보내는 부분은 `perception/map_maker.py` 다 (아래 「드론 사진 → 지도 발행」).

```python
b = detect_boundary(img); view = detect_boxes(img, b)
fm = view.field_map(b, stamp=찍은_시각_초)          # dict — 칸 이름이 FieldMap.msg 와 같다 (JSON 저장 · 시험용)
msg = drone_field_map.field_map_msg(fm)             # ROS 2 환경에서 team_interfaces/FieldMap 메시지로
```

- 채우는 칸: `header`(frame_id `arena`, stamp = 사진 찍은 시각) · `width` · `height` · `box_size` · `boxes` · `sectors`(이 화면에서 잰 끝 띠 · CM 반폭으로 7개) ·
  `faces`(상자마다 E · N · W · S, 다른 상자와 맞닿은 면은 뺌, `image_ref` 빈 문자열) · `beam_depth` 0.20.
- 비우는 칸: `vehicles` (드론 사진의 UGV 찾기는 아직 없다). navigation slam 은 2026-11-18 부터 SELF 없이, `bases` 중 이름이 우리 자리(`B-1` 등)인 칸에서 출발 위치를 찾는다.
- `bases` (노드는 `base_naming="slot"` 으로 내보낸다 — supervisor 가 2026-11-18 부터 두 이름을 모두 읽는다): 받는 쪽이 이름을 다르게 읽는다 — supervisor 는 보고값(`BLUE_COMMAND_POST` 등, 비면 도면 기본값),
  navigation slam 은 호출부호(`B-1` 등). 기본은 비움. `base_naming="slot"` 이면 `B-1`~`R-3`, `"report"` 이면 보고값(줄마다 거점 종류 `base_kinds` 필요).
  범위는 도면값(벽에서 0.40 m, 줄 가운데 ±0.60 m).

- **높이 보정 (시차)**: 경계 대응은 바닥(높이 0) 전용이다. 상자 윗면(높이 0.4 m)은 카메라 바로 아래 점 N 에서 s = Hc/(Hc − 0.4) 배 먼 곳으로
  밀려 보인다 → 상자 가운데 = N + (윗면 가운데 − N)/s. 보정하지 않으면 경기장 끝 쪽 상자는 30 cm 넘게 바깥으로 간다.
  - N = 경기장 정중앙 (현장 확인 2026-11-18: 연습 · 본선 모두 카메라 x, y 가 정중앙, 건물 천장에 붙어 있음).
  - s(카메라 높이)는 카메라 쪽 옆면의 폭으로 잰다 (면마다 재서 중앙값). 연습 화면 두 대 모두 약 2.5 ~ 2.7 m. 알면 `BoxParams(camera_height=…)` 로 준다.
- **찾는 법**: 바닥 지도로 편 뒤, 경계 모델이 아는 바닥 선을 지우고 네 변이 곧은 정사각형(윗면)을 찾는다. 이 화면 윗면들과 크기가 다른 것 ·
  노란 것(거점 테두리 · 줄무늬 벽 블록) · 끝 띠 안 · 카메라 쪽 옆면 자리가 바닥인 것 · 겹치는 것을 버린다. 버린 후보와 까닭은 `rejected` 에 남는다.
- **검증** (2026-11-18):
  - 합성 장면 (정답을 아는 그림, 카메라 2.6 · 3.5 m): 상자 14/14, 위치 오차 최대 약 5 cm, 잰 카메라 높이는 실제보다 약 2 % 낮음.
  - 연습 화면 test1 · test2 각 1장: 상자 14/14 (오탐 0). test2 의 붙은 상자 쌍 6개 간격 0.37 ~ 0.42 m (정답 0.40), 좌우 대칭 자리 차이 2.5 cm 이내.
  - 수집 화면 일괄 (17:12 ~ 19:51, 25장에 1장): test2 경계가 맞은 36장 중 34장 14/14 · 2장 13개, 상자마다 화면 간 흔들림 1 ~ 2.5 cm,
    카메라 높이 중앙값 2.68 m (사분위 2.55 ~ 2.75). test1 은 연습 팀들이 중간에 상자를 옮겨 정답이 바뀐다 — 같은 배치인 17:16 ~ 17:58 11장은
    모두 14개 · 흔들림 7 cm 이내. test1 카메라 높이는 2.9 ~ 3.2 m 로 더 크고 더 흔들린다 (test1 렌즈값이 화면마다 흔들리는 것과 같은 원인으로 본다).
- **알려진 한계**:
  - 경계 지도의 축척 오차를 그대로 물려받는다 — A4 용지로 잰 test2 지도는 x 비율 0.97 ~ 1.07, **y 비율 1.02 ~ 1.15** (세로가 늘어나 있다).
  - 노란 줄무늬 벽 블록 · 끝 띠 안 물체는 내지 않는다. 경기장 축에서 돌아간 상자 · 사람이 가린 상자는 놓칠 수 있다.
    경기장 안에 사람이 있으면 사람 위에 상자가 잘못 잡힌다 (연습 17:12 화면 3개).
  - 경계가 구역선을 잘못 고른 화면(끝 띠 · CM 반폭이 연습 경기장 값과 다름)은 상자를 찾되 `ok=False` 와 notes 로 알린다.
  - 카메라 높이는 화면마다 ±5 % 흔들린다 → 경기 중에는 처음 몇 장의 중앙값으로 고정해 쓰는 것이 낫다 (도구가 중앙값을 알려 준다).

### 경기 중 드론 사진 → UGV 자리 발행 (2026-11-19 밤, 구현 중 — navigation 담당이 붙임)

경기 중 드론 사진마다(약 1 Hz) UGV 를 찾아 `/team/perception/ugvs`(`geometry_msgs/PoseArray`, frame `arena`)로 낸다. navigation 이 막힘 판단 · 기억 정리 ·
지도 고치기에 쓴다 ([navigation README](../navigation/README.md) 「드론이 본 UGV 자리 쓰기」).

| 파일 | 하는 일 |
|---|---|
| `perception/drone_ugvs.py` | 계산: map 그림(상자 모델과 같은 그림) → UGV 모델 → 가운데 → UGV 높이로 고친 지도 좌표. ROS 없이 돈다 |
| `perception/ugv_watch.py` | 노드 연결: 드론 사진 구독 · 따로 도는 스레드에서 판독 · 발행 · 기록 |
| `test/test_drone_ugvs.py` | 단위 시험 4개 (가짜 카메라 · 가짜 예측기) |

- **지도가 나온 뒤부터 돈다.** 그 지도를 만든 사진의 경계 · 카메라 높이 · 지도 크기를 그대로 쓴다 (`map_maker.view_info` — `compute` 가 `info["view"]` 로 넘긴다).
  그래서 지도와 같은 좌표다. 벽만 있는 임시 지도뿐이면 돌지 않는다.
- **모델**: `training/drone_boxes` 의 `ugv_v1` (클래스 `ugv` 하나, 우리 차 · 다른 차를 가리지 못한다). `/home/ws/team/models/drone_ugvs.engine` → 같은 이름의 `.pt` →
  git 에 넣은 `training/drone_boxes/trained/drone_ugv_v1.pt` 순으로 찾는다. 그림 모델과 같은 장치에서 돈다 (`ugv_watch_device` 로 바꿈). 못 읽으면 끄고 `node_status` detail 에 남긴다.
- **높이 고치기**: map 그림은 상자 윗면(0.40 m) 평면으로 편 것이라 그보다 낮은 UGV 는 화면 가운데 쪽으로 끌려 찍힌다 (카메라 2.55 m, 가운데에서 2.5 m 면 약 17 cm).
  그 픽셀의 바닥 점에서 `ugv_watch_height`(기본 0.10 m) 평면의 점으로 되돌린다. 0.10 은 공식 테스트 경기 6판(본선 카메라)의 사진에 이 모델을 돌려 우리 차의 드론 자리를
  그때의 라이다 위치와 견줘 맞춘 값이다 (441장: 0.00 → 바깥쪽 +0.05 m · 0.10 → −0.01 · 0.20 → −0.07). 연습 카메라로는 재지 않았다. navigation 기록의 `ugvs.self_off` 로 다시 맞춘다.
- **내보내는 것**: UGV 마다 `position.x · y` = 가운데 (m), `position.z` = 점수. 우리 차도 들어 있다. 한 대도 없으면 빈 목록. `header.stamp` = 그 드론 사진의 stamp
  (server_bridge 가 받은 시각 — 사진은 0.3 ~ 0.7 s 앞서 찍혔다).
- **안 보이는 곳**: 화면 위아래가 잘린다. UGV 높이에서 보이는 세로 범위(4.80 지도)는 본선 카메라 0.33 ~ 4.17 m (2026-11-20 다시 잼 — 맞게 찾은 경계 · UGV 높이 0.10. 공식 테스트 경기 여섯 판에서 우리 차가 잡힌 비율: y 0.6 ~ 3.9 에서 99 %, 3.9 ~ 4.15 에서 82 %, 4.15 위에서 15 %, 0.35 아래에서 18 %), 연습 test1 0.23 ~ 4.43 · test2 0.33 ~ 4.46 (실차 기록의 값은 0.24 ~ 4.55).
  경기마다의 값은 기록(`perception/ugvs.jsonl` 의 `view` 줄 `seen_y`)에 남는다.
- 매개변수: `ugv_watch`(true) · `ugv_watch_model` · `ugv_watch_conf`(0.5 — 학습 기록의 검증 기준) · `ugv_watch_height`(0.10) · `ugv_watch_min_s`(0.5) · `ugv_watch_device`.
- 기록: `TEAM_LOG_DIR/perception/ugvs.jsonl` 에 사진마다 한 줄 (자리 · 점수 · 걸린 ms).
- **사진이 뜸해지거나 끊긴다** (공식 규정): 우리 진영 시설물이 1개 파괴되면 2 s · 2개면 5 s 간격, 3개면 403. 이 프로그램은 오는 사진마다 한 번 낼 뿐이고, 받는 쪽(navigation)이 간격에 맞춘다.
- **확인한 것**: PC 단위 시험, 그리고 공식 테스트 경기 6판의 본선 카메라 사진 819장에 진짜 모델(`drone_ugv_v1.pt`, PC CPU · ultralytics 8.4.215)을 이 코드로 돌린 것 —
  장당 3 ~ 7대 · 겹쳐 찾은 것 없음 · 장당 약 75 ms. **로봇에서는 돌려 보지 않았다**: 판독 시간 · 메모리 · 그림 판독 서비스와 함께 돌 때의 영향은 미확인이다.

## 필수 작업 지침

- 작업 전 [공통 규칙](../../AGENTS.md), [통신 계약](../../../노드_관리/interfaces.yaml), [타입 정의](../team_interfaces/)를 읽는다. 노드 id는 `perception`이다.

- 다른 노드나 공통 타입 수정은 사전 승인을 받고, 연결된 노드의 영향을 확인한다.
- 현재 파일 존재만으로 구현 완료 처리하지 않는다. 구현 상태와 실제 소스 경로를 YAML에 맞춘다.
