# 가설 검토 (2026-11-18, UGV-08)

[로그_분석.md](로그_분석.md)에서 세운 가설을 로봇 소스(`ugv_base_node/src/base_node.cpp`, `mil_base/base_node.py`)와 실시간 조회로 검토했다. 이 시험의 결론이 크게 바뀐 부분은 H1·H4다. 로봇은 움직이지 않았고 읽기만 했다.

## 검토 결과 요약

| # | 가설 | 판정 | 근거 |
|---|---|---|---|
| H1 | `/odom` yaw가 0으로 죽어 있다 | **원인 확인.** 단 "휠 방향이 없다"가 아니라 "발행하지 않는다" | `base_node.cpp`: 발행 orientation은 IMU 구독값(`imu/data`)을 그대로 싣는다. launch가 `imu/data`를 `imu/data_unused`로 돌려 구독이 비고, 초기값 `w=1`이라 항상 단위 사원수. 실시간 `/odom` orientation = (0,0,0,1) |
| H2 | 회전 중 `/odom`이 거의 아무것도 보고하지 않는다 | **원인 확인** (1 cm 양자화) | `odom_raw`는 1 cm 해상도(값 `-0.51, 0.77`), 약 19.7 Hz. 속도는 마지막 간격의 순간값이고 `/odom`은 10 Hz 타이머로 발행 |
| H3 | 직진 속도가 0/0.1/0.2로 튄다 = 모터 피드백이 약 5 Hz | **원인 확인, 5 Hz 가설은 틀림** | 피드백은 약 20 Hz. 50 ms에 한 바퀴가 1 cm 눈금을 넘으면 0.2(0.01 m/0.05 s), 한 바퀴 평균이면 0.1, 못 넘으면 0 |
| H4 | `/odom` 위치가 비스듬한 건 내부 방향이 돌아서다 | **확인** | 아래 표. 위치 증분의 방향이 24° → 약 115° → 65°로 변하고, 변화량이 실제 회전과 맞다 |
| H5 | 0.3 rad/s는 데드밴드(마찰) 때문에 거의 안 돈다 | **미확인(여전히 가능성 높음)** | 내부 방향 변화로도 "우 90° 명령 ≈ −11°, 좌 180° 명령 ≈ +90°"가 나와 사용자 관찰과 독립적으로 맞는다. 원인이 마찰인지 모터 편차인지는 가려지지 않음 |
| H6 | 회전이 시간에 비례하지 않는다(비선형) | **미확인** | 좌/우와 시간이 함께 달라 분리 불가. 같은 조건 반복 시험 필요 |
| H7 | 바퀴 간격 0.175 m 가정이 맞다 | **미확인** | 소스에 하드코딩. 스키드 조향은 미끄러져서 실제 유효 간격이 더 클 수 있음. 각도기로 보정 필요 |
| H8 | `/imu/data`로 회전을 잴 수 있다 | **미확인** | `imu_filter_madgwick`이 20 Hz로 orientation을 낸다(정지 상태 z −0.98, w −0.20). 정지 자이로 z는 −0.006 rad/s로 살아 있어 보이나, launch 주석은 ESP IMU(ICM-20948 DMP)가 값을 고정한다고 적었다. 회전하며 변하는지 확인 안 함 |

## H4 근거: 위치 증분 방향으로 본 내부 방향

`/odom`의 x, y는 `x += cos(yaw)·dx − sin(yaw)·dy` 식으로 내부 `yaw`(`odom_yaw`)를 써서 적분된다. 따라서 이동마다 위치 증분의 방향 atan2(dy, dx)가 내부 방향을 보여 준다(후진은 180° 보정). 정밀도는 낮다(회전 중 증분은 1~2 cm).

| 이동 | 명령 | 증분 방향(내부 방향 추정) |
|---|---|---|
| #1, #2 | 후진 0.1 m | 24° |
| #3 | 좌 180° | (증분 0.009 m, 방향 불안정) |
| #4 | 우 90° | 119.5° |
| #5 | 우 90° | 112.9° |
| #6 | 우 90° | 98.2° |
| #7 | 우 90° | 86.8° |
| #8 | 우 90° | 75.3° (증분 0, 신뢰 낮음) |
| #9 | 전진 0.5 m | 64.5° |
| #10~#13 | 전·후진 0.1 m | 65~67° |
| #16 | 우 90° | 60.6° |

- #2 → #4: 24° → 약 115~120°, 즉 좌 180° 명령 한 번(#3)에 **약 +90°**. 사용자가 본 "약 90°"와 일치한다.
- #4 → #9: 119.5° → 64.5°, 우 90° 명령 5번(#4~#8)에 약 −55°, 회당 **약 −11°**. 사용자가 본 "약 10°"와 일치한다.
- 순 변화량: 24° → 65° = +41°, 기대값 +90° − 5×11° = +35°. 서로 맞는다.

## 숫자 확인 (소스와 로그가 같은 값을 내는지)

- 한 바퀴 한 눈금(1 cm), `dt` 50 ms에서 `wz = 0.01/0.175/0.05 = 1.14 rad/s`, 두 눈금이면 2.3. 로그의 `wz` 최대값 1.14~1.21, 2.38~2.59와 일치.
- `vx = 0.005/0.05 = 0.1`, `0.01/0.05 = 0.2`. 로그의 0.1, 0.2와 일치.

## 이 검토가 정정하는 이전 서술

- "`/odom` 방향이 죽어 있다 / 회전을 전혀 측정할 수 없다" → "발행된 `/odom`으로는 못 재지만, 내부 휠 방향은 회전을 따라간다. `odom_raw`로 직접 계산 가능."
- "모터 피드백이 약 5 Hz로 온다" → 틀림. 약 20 Hz이고 문제는 1 cm 양자화.
- "직진 `/odom` 방향 오차" → 오차가 아니라 내부 방향으로 적분되는 정상 동작이며, 발행 yaw가 상수라서 밖에서는 비스듬히 보인다.

## 한계

- 내부 방향은 직접 기록한 값이 아니라 위치 증분 방향으로 역산한 것이다(오차는 ±10° 안팎으로 보는 것이 안전하다).
- 사용자가 본 회전 각도는 눈대중이다. 줄자·각도기 실측은 없다.
- 좌/우 비대칭, 시간 비선형, 0.175 m 가정, `/imu/data` 추종은 확인하지 못했다.

## 다음 시험 제안 (움직임 포함 여부 표시)

1. 웹 조종 서버(`도구/teleop_server.py`)가 `/odom/odom_raw`를 같이 기록하고 그 값으로 계산한 방향(Δθ)을 결과 표에 보여 주도록 한다(코드 수정, 기존 토픽 구독만 추가; 팀 코드에 넣을 때는 사용자 승인 필요). 
2. (이동 없음) 로봇을 손으로 돌려 보며 `/odom/odom_raw` 방향과 `/imu/data` 방향이 각도기 값과 맞는지 확인한다.
3. (이동 있음) 같은 조건 반복: 좌 90° 5회, 우 90° 5회로 재현성과 좌우 차이 확인.
4. (이동 있음) 회전 속도 0.3 → 0.8 → 1.5 rad/s로 올려 실제 각도를 재서 필요한 최소 속도를 찾는다. 서버 `MAX_ANG`(0.8)를 올려야 한다(브리지 상한 3.0).
5. 줄자로 직진 0.5 m·1 m 실측을 웹 화면 실측 칸에 입력한다.
