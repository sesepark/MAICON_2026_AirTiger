# 연습 경기장에서 supervisor를 볼 때의 순서

2026-11-18 작성. supervisor는 가짜 상대와만 돌려 봤다. 실제 로봇에서는 아래 순서로 하나씩 확인한다.
앞 단계가 안 되면 뒤 단계는 볼 수 없다. 재서 얻은 값은 로봇의 `~/team/supervisor.json`에 적는다 (형식은 [README](../README.md)의 「설정」).

로봇에 올리는 방법은 [개발/robot/README.md](../../../robot/README.md).

## 1. 켜지는가

- 로봇에서 `cd ~/team && python3 team_node.py` (Jupyter 셀에서는 `!cd /home/jetson/team && python3 team_node.py`)
- 보여야 하는 것: `[team_node] 켬: …` 줄들과 `supervisor 켜짐 (run_id …)`
- `팀 작업공간이 없습니다`가 나오면 `~/team/ws`에서 `colcon build`를 안 한 것이다
- 경기 신호 없이 볼 때는 `supervisor.json`에 `{"force_start": true, "slot": "B-1"}`

## 2. 다른 프로그램의 것이 오는가

다른 터미널(컨테이너 안)에서 확인한다.

| 볼 것 | 명령 | 맞는 모습 |
|---|---|---|
| 로봇 위치 | `ros2 topic hz /team/navigation/pose` | 1초에 10번 이상 |
| 위치 값 | `ros2 topic echo /team/navigation/pose --once` | 로봇을 아는 자리(예: 우리 거점 가운데)에 두었을 때 그 좌표 |
| 지도 | `ros2 topic echo /team/navigation/map --once` | `boxes`의 개수와 위치가 실제 상자와 같다. `frame_id`가 `arena` |
| 사진 | `ros2 topic hz /image_raw` | 1초에 19장쯤 |
| supervisor가 내보내는 것 | `ros2 topic echo /team/mission/state --once` | `phase`, `slot`, `detail`(지금 하는 일) |

supervisor의 `하는 일`이 `wait-map`에서 안 넘어가면 지도가, `wait-pose`면 위치가 안 오는 것이다.

## 잰 값 (2026-11-18, 8호기) — 3 · 4번은 이것으로 끝났다

로봇을 상자 면 앞에 세워 두고 팬틸트를 돌려 가며 사진 17장을 찍어, 그림 위 초록 불빛이 사진에서 옮겨 간 픽셀을 쟀다 (기록: `로그_파일/1118_카메라_팬틸트_측정/`).

- **가로 화각 127.4°** (세로 95.5°). 팬 1단위에 2.51 픽셀 → 팬 1단위 0.5°로 치면 1도에 5.02 픽셀. `CameraParams`의 기본값을 이 값으로 바꿨다 (그 전 추정 120°)
- **렌즈는 각도에 비례해 찍힌다** (광축에서 −30° ~ +50° 범위에서 직선과의 차이 최대 1.2 픽셀). 일반 렌즈(tan) 식으로는 27 픽셀이 어긋난다 → `lens: "equidistant"` 그대로
- **틸트 1단위 = 0.30°** (팬 0.5° 기준 0.298°). 공식 뼈대의 값이 맞고, 로봇 안 정의 파일 주석의 0.15°는 맞지 않는다. 범위 ±30°
- 방향: 팬 + = 오른쪽, 틸트 + = 위 (사진에서 확인)
- 정면의 40 cm 면이 106 픽셀 = 21.1° → 렌즈에서 면까지 1.07 m. 로봇을 「면 앞 1 m」에 세웠다고 했으니 팬 1단위 0.5°와 앞뒤가 맞는다
- 남은 오차: 불빛이 1 m 남짓 거리에 있어, 렌즈가 팬 회전축에서 앞뒤로 3 cm 떨어져 있다면 화각이 3%쯤(124° ~ 131°) 달라질 수 있다. 사진과 면을 짝지을 때 사진마다 배율을 다시 맞추므로 이 정도는 흡수된다

다른 로봇을 쓰게 되면 같은 방법으로 다시 잰다: 콘솔이나 `/mil/gimbal`로 팬을 −80 ~ +80, 틸트를 −60 ~ +60까지 20단위씩 돌리며 사진을 찍는다.

## 3. 카메라가 가로로 몇 도를 찍는가

1. 로봇을 상자 한 면의 정면 1.0 m 앞에 둔다 (렌즈에서 면까지)
2. 사진 한 장을 저장해 그 면(폭 40 cm)이 가로로 몇 픽셀인지 잰다 → `w`
3. 가로 화각 = `640 × 22.6 ÷ w` 도. 예: `w`가 120이면 120°, 90이면 161°, 180이면 80°
4. `supervisor.json`에 `{"camera": {"hfov_deg": 값}}`

사진 가장자리로 갈수록 많이 휘는 렌즈라면 가운데에서 잰 값과 가장자리가 다르다. 그때는 상자를 사진 가장자리에 두고도 한 번 잰다.

## 4. 팬틸트

- 팬에 +20을 보냈을 때 카메라가 **오른쪽**으로 10° 도는지 (1단위 0.5°)
- 틸트에 +50을 보냈을 때 위로 몇 도 올라가는지: 15°면 1단위 0.3°(공식 뼈대), 7.5°면 0.15°(사전교육 자료) → `{"gimbal": {"tilt_deg_per_unit": 값}}`
- 보낸 뒤 멈출 때까지 걸리는 시간 → `{"gimbal": {"settle_s": 값}}` (기본 0.6초)

## 5. 사진 한 장의 판독과 짝짓기

1. 로봇을 상자 앞 1 m쯤에 세운다
2. supervisor가 돌고 있으면 `~/team/log/<날짜_시각>/supervisor/photos.jsonl`에 사진마다 한 줄이 쌓이고, 보낸 사진은 그 옆 `photos/`에 남는다
   - `expected`: 그 자리에서 찍혀야 한다고 계산한 면들 (왼쪽부터, `x`는 사진 속 가로 위치 0~1)
   - `pictures`: perception이 답한 그림들
   - `pairs`: 짝지어 적은 결과. `null`이면 그 사진을 버린 것이다
3. 볼 것
   - `expected`의 면이 실제로 그 순서로 보이는가 → 아니면 위치나 지도가 틀린 것이다
   - `pictures`의 `x`와 `expected`의 `x`가 비슷한가 → 한쪽으로 일정하게 밀리면 로봇 방향이, 가장자리로 갈수록 벌어지면 화각 값이 틀린 것이다
   - `pairs`가 자주 `null`인가 → `pictures`의 개수와 `expected` 중 `sure`인 면의 개수를 견준다

## 6. 정찰 두 방식

`supervisor.json`의 `scout_mode`를 `"place"`와 `"face"`로 바꿔 한 번씩 돌린다. 같은 상자 배치 · 같은 출발 자리에서.

적어 둘 것: 정찰이 끝난 시각(기록의 `정찰 끝`), 적은 면의 비율, 사람이 정답과 견줘 틀린 면의 수, 못 적은 면의 수.

가상 시험에서는 `place`가 더 빠르고 더 맞았다. 다만 가짜 인식은 작은 그림도 다 알아보므로 실제 인식에서는 다를 수 있다.

## 7. 지정표적

1. M1 해석이 오는지 (기록의 `M1 해석: …`)
2. 정찰 중 표적 면을 찾으면 `지정표적 … 발견`이 찍히고 쏠 자리로 간다
3. 발사 뒤 표적 위의 빨간 불이 켜지는지 (서버는 알려 주지 않는다)
4. 안 맞으면: 빔이 위·아래로 빗나갔는지 보고 `{"mission": {"emitter_height": 값, "target_receiver_height": 값}}`, 좌우면 3번(화각)과 2번(위치)을 다시 본다

## 8. 4:00 대기와 진입

- 3분 40초쯤 `하는 일: stage`가 찍히고 우리 줄의 상대 거점 앞(벽에서 0.60 m)에 서는가
- 4:00에 `하는 일: assault`가 찍히고 게시된 거점 안으로 들어가는가
- 엉뚱한 거점으로 가면 지도(`/team/navigation/map`)의 `bases`에서 이름과 줄(`row`)이 실제와 같은지 본다

## 9. 끝나는가

- 경기 종료 신호(`report` 다음 `stop`) 뒤 `team_node.py`가 1.5초 안에 끝나는가
- `ps`로 팀 프로그램이 남아 있지 않은지 본다

## 10. 서버와 LLM

`~/team/secrets.json`에 서버 주소 · 임무코드 · LLM 키를 넣은 뒤 (형식은 `개발/robot/secrets.example.json`).

- `~/team/log/<날짜_시각>/server_bridge.log`에 `서버 단계 … · 자리 …`가 찍히는가. `GET /me 실패가 이어짐`이면 주소나 망을 본다
- supervisor 기록에 `M1 해석: …`이 명령문을 받고 몇 초 안에 찍히는가. `llm_worker.log`의 `LLM 요청 끝 (…초): LLM 반영`이면 LLM까지 된 것이고, `LLM 실패`면 낱말 해석만 쓴 것이다
- 연습 기간에 드론 사진을 받으려면 `~/team/server_bridge.json`에 `{"drone_camera": "test1"}` (경기 때는 이 줄을 지운다 — API 문서 4단계)

## 10-1. 포털의 팀 테스트로 한 판 돌리기

포털(`http://<서버 IP>:8000/test`) → 「테스트 대시보드」. 자세한 흐름은 [포털에서_확인한_것.md](포털에서_확인한_것.md) 2절.

1. 「팀 테스트 준비」에서 호출부호와 시험 임무를 정한다 (M3는 구역별 객체 종류 · 수량을 실제 놓은 대로 적는다 — 끝난 뒤 정답 비교에 쓰인다)
2. 로봇을 그 호출부호의 출발 거점 안에 상대 진영을 보게 놓는다
3. 로봇에서 `cd ~/team && python3 team_node.py` — `~/team/supervisor.json`에 `force_start`가 있으면 지운다 (서버 단계를 따라야 한다)
4. 포털의 준비완료가 「받음」이 되면 「시작」. 5초 뒤 0:00
5. 5:30에 서버 단계가 `finished`가 되면 `team_node.py`가 스스로 끝난다. 포털에 M1 · M3 정답 비교가 나온다

server_bridge는 시험 포트(8100)를 스스로 고른다 (`server_bridge.log`에 `서버를 …:8100 로 정함`). 설정은 본 경기와 같은 것을 그대로 쓴다.

## 11. 기록을 가져오기

돌릴 때마다 `~/team/log/<날짜_시각>/` 폴더 하나가 생긴다 (위치 · 하는 일 · 이동 · 사진 · 판독 답 · 발사 · 보고 · 서버 요청 · LLM 요청). 연습이 끝나면:

```bash
cd ~/team && python3 team_node.py --pack-logs        # 사진을 빼려면 뒤에 --no-photos
```

만들어진 `team_logs_<날짜_시각>.tgz`를 내려받아 저장소의 `로그_파일/`에 넣고 올린다 ([로그_파일/README.md](../../../../로그_파일/README.md)). 그때의 상황(상자 배치, 출발 자리, 무엇을 보려 했는지, 눈으로 본 결과)을 같이 적어 둔다.
